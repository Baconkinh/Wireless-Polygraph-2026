## 1. หลักการตั้งชื่อและเลขอ้างอิง

**คำถามหนึ่งข้อมีเลข 2 แบบ**

- `question_no` / `question_order` = ลำดับข้อที่คนอ่าน (1, 2, 3 ...) นับใหม่ทุกรอบ/ทุกเซสชัน
- `watch_qid` / `qid` = เลขที่ Studio ส่งให้นาฬิกาตอนเริ่มข้อ นาฬิกาส่งผลกลับมาพร้อมเลขนี้ จึงจับคู่ "ผล" กับ "คำถาม" ได้ถูกข้อ

**ช่วงของ qid (กันชนกันเมื่อหลายโปรแกรมถามพร้อมกัน)**

| ช่วง qid | ใครเป็นคนถาม |
|---|---|
| 1 – 499 | เซสชันทดสอบใน Studio (หน้าหลัก ฝั่งซ้าย) |
| 500 – 599 | ควบคุมด่วนทีละข้อ (หน้าหลัก ฝั่งขวา) |
| 600 – 799 | หน้าเก็บข้อมูลเทรน AI, หน้าใช้งานจริง และ collect_data.bat |
| 800 – 899 | คำสั่ง `ask` ใน Serial Monitor |
| 900 – 999 | ปุ่ม BOOT บนนาฬิกา |

**เฉลย (label)** ใช้คำภาษาอังกฤษเสมอ

| ค่า | ความหมาย |
|---|---|
| `truth` | ผู้ตอบพูดจริงในข้อนี้ (label ตัวเลข = 0) |
| `lie` | ผู้ตอบโกหกในข้อนี้ (label ตัวเลข = 1) |
| `unknown` | ไม่รู้เฉลย (manual กดข้าม / live กด "ไม่ทราบ") — ไม่นำไปเทรน |
| `aborted` | ข้อนี้ถูกยกเลิกกลางทาง — ไม่นำไปเทรน |

**โหมด (mode)** ของแต่ละข้อ — บอกว่าเฉลยได้มาอย่างไร

| ค่า | เฉลยได้มาจาก |
|---|---|
| `fix` | ผู้ถามบอกผู้ตอบ "ก่อนถาม" ว่าข้อนี้ให้ตอบจริงหรือให้โกหก |
| `manual` | ผู้ตอบเลือกเองว่าจะจริงหรือโกหก แล้วบอกหลังได้ผล |
| `live` | ใช้งานจริง: นาฬิกาตัดสินก่อน แล้วผู้ใช้บอกว่านาฬิกาตอบ ถูก/ผิด → แปลงเป็นเฉลย (ดูคอลัมน์ `feedback`) |
| `watch` | นาฬิกาบันทึกเอง (โหมด train บนหน้าเว็บนาฬิกา ข้อควบคุมที่รู้เฉลย) แล้วดึง/นำเข้ามา |
| `legacy` | แถวจาก training_samples.csv รุ่นเก่าที่ไม่มีคู่ใน results_ |

**ช่วงเวลา (phase)** ของแต่ละแถวสัญญาณ

| ค่า | ความหมาย |
|---|---|
| `baseline` | กำลังวัดค่าปกติ (~30 วินาที) |
| `rest` | นั่งพัก ไม่ได้ถาม |
| `question` | 12 วินาทีหลังถาม (ช่วงที่นาฬิกาใช้ตัดสิน) |
| `recovery` | หลังได้ผลแล้ว ระหว่างรอเฉลย/ร่างกายกลับสู่ปกติ |

**ใครตัดสินว่าจริงหรือโกหก?** นาฬิกาเป็นคนตัดสินเสมอ (LieEngine หรือโมเดล AI ถ้าติดตั้งแล้ว) จากสัญญาณ 12 วินาทีหลังถาม
ส่วนปุ่ม `y / n` (ผู้ถูกทดสอบตอบ ใช่/ไม่ใช่) แค่บันทึกว่าเขาตอบอะไร ไม่ได้เปลี่ยนคำตัดสิน
และเฉลย (`truth / lie`) ในโหมดเก็บข้อมูล คือ "คำตอบที่ถูก" ที่เราบอกให้ AI เรียนรู้ ไม่ได้เปลี่ยนคำตัดสินของนาฬิกาเช่นกัน

## 2. `data/signals/signals_<run_id>.csv` — ค่าเซนเซอร์ทุกแถว (5 แถว/วินาที) — ไม่ได้ใช้เทรน

สร้างโดยหน้า "เก็บข้อมูลเทรน AI", "ใช้งานจริง" และ `collect_data.bat` (โค้ด `ml/recorder.py`) คู่กับ `result_<run_id>.csv` ชื่อเดียวกัน
ไฟล์ถูกสร้างตอนเริ่มข้อแรกเท่านั้น — ช่วง baseline ก่อนหน้าจะถูกเขียนตามลงไปทีหลัง

| คอลัมน์ | หน่วย | ความหมาย / มาจากไหน |
|---|---|---|
| `time_iso` | วันเวลา | เวลาในคอมตอนได้รับค่า |
| `t_sec` | วินาที | เวลานับจากเริ่มรอบ |
| `run_id` | - | รหัสรอบ = วันเวลาที่เริ่ม (ตรงกับชื่อไฟล์) |
| `subject` | - | ชื่อผู้ถูกทดสอบ |
| `phase` | - | baseline / rest / question / recovery (ดูข้อ 1) |
| `question_no` | - | ข้อที่เท่าไรในรอบนี้ (ว่าง = ไม่อยู่ในข้อใด) |
| `watch_qid` | - | qid ที่ส่งให้นาฬิกา (600 + ลำดับ) |
| `mode` | - | fix / manual / live (ดูข้อ 1) |
| `label` | - | เฉลยของข้อนั้น: truth / lie / unknown / aborted |
| `hr_bpm` | ครั้ง/นาที | อัตราการเต้นหัวใจ จาก MAX30102 (หาจุดยอดของคลื่น PPG) ว่าง = เซนเซอร์ไม่แตะผิว |
| `hrv_ms` | มิลลิวินาที | ความแปรปรวนของจังหวะหัวใจ (RMSSD ของช่วงห่างระหว่างครั้ง) |
| `ppg_contact` | 0/1 | 1 = เซนเซอร์ชีพจรแตะผิว (แสง IR สะท้อนกลับเกินเกณฑ์) |
| `gsr_us` | µS (ไมโครซีเมนส์) | ความนำไฟฟ้าของผิว = 1 / ความต้านทานผิว จากแผ่น GSR ผ่าน ADC GPIO1 — สูงขึ้นเมื่อเหงื่อออก |
| `gsr_tonic_us` | µS | ระดับพื้นฐานที่เปลี่ยนช้า (ค่าเฉลี่ยเคลื่อนที่แบบ EMA ค่าคงที่เวลา 15 วินาที) |
| `gsr_phasic_us` | µS | ส่วนที่พุ่งขึ้นเร็ว = gsr − tonic (การตอบสนองต่อสิ่งเร้า) |
| `gsr_contact` | 0/1 | 1 = แผ่น GSR แตะผิว (ไม่มีเหงื่อ/ผิวแห้ง = 0 ระบบยังทำงานต่อได้) |
| `skin_temp_c` | °C | อุณหภูมิผิวจาก NTC 10k (สมการ Beta 3950) |
| `tremor_ms2` | m/s² | ความแรงการสั่นของมือ ช่วง 3–15 Hz จาก MPU6050 (band-pass filter) |
| `motion_ms2` | m/s² | การขยับแขน/ตัว ช่วง 0.3–3 Hz (ถ้ามากจะทำให้ข้อนั้นใช้ไม่ได้) |
| `stress_index` | 0–100 | ดัชนีความตื่นตัวรวมจากทุกสัญญาณ (ว่าง = ยังไม่วัด baseline) |
| `engine_state` | - | สถานะสมองตัดสินในนาฬิกา: idle / baseline / ready / question |
| `battery_mv` | mV | แรงดันแบตเตอรี่ (ADC GPIO4 ผ่านตัวแบ่ง 1/2) |

ตัวอย่างการใช้: กรองแถว `phase = question` แล้ว group ตาม `question_no` จะได้กราฟสัญญาณของแต่ละข้อ พร้อมเฉลยใน `label`

### ไฟล์ signals รุ่นเก่า (สร้างก่อนวันที่ 8 ต.ค. 2569)

คอลัมน์ `pc_time, watch_ms, mode, state, qid, hr, hrv, ppg_contact, gsr, gsr_tonic, gsr_phasic, gsr_contact, skin_temp, tremor, motion, stress, vbat_mv`
มีความหมายเหมือนตารางข้างบน (ชื่อย่อ) ข้อเสียคือ `qid` ใส่เฉพาะตอนกำลังถาม และ **ไม่มีเฉลย** — รุ่นใหม่แก้แล้ว

| ชื่อเก่า | ชื่อใหม่ |
|---|---|
| `pc_time` | `time_iso` (epoch วินาที → วันเวลา) |
| `watch_ms` | เวลาในนาฬิกา (มิลลิวินาทีตั้งแต่บูต) — รุ่นใหม่ใช้ `t_sec` แทน |
| `mode` | 1 = นาฬิกาอยู่โหมดเก็บข้อมูล, 0 = ใช้งานจริง |
| `state` | `engine_state` เป็นตัวเลข 0 idle, 1 baseline, 2 ready, 3 question |
| `hr, hrv, gsr, skin_temp, tremor, motion, stress, vbat_mv` | `hr_bpm, hrv_ms, gsr_us, skin_temp_c, tremor_ms2, motion_ms2, stress_index, battery_mv` |

## 3. `data/result_<run_id>.csv` — 1 แถวต่อข้อ (ไฟล์ที่ใช้เทรน AI)

`train_ai.bat` และปุ่ม "เทรน AI" อ่าน **เฉพาะ** ไฟล์ชื่อ `result_<YYYYMMDD_HHMMSS>.csv` ในโฟลเดอร์ `data/` (ไม่อ่านโฟลเดอร์ย่อย)
และในแต่ละไฟล์ใช้เฉพาะแถวที่ `used_for_training = 1` และ `label` เป็น truth/lie
ไฟล์ใหม่มี BOM ทำให้เปิดใน Excel แล้วภาษาไทยถูก — **อย่า Save ทับจาก Excel** (Excel เปลี่ยนรูปแบบเวลา เช่น `16:48:58.012` เป็น `48:58.0`)

| คอลัมน์ | ความหมาย |
|---|---|
| `time_iso` | เวลาที่บันทึกข้อนี้ (เวลาคอม) |
| `run_id` | รหัสรอบ = วันเวลาเริ่มรอบ (ตรงกับชื่อไฟล์) |
| `source` | มาจากไหน: `studio` (หน้าเว็บ), `cli` (collect_data.bat), `watch` (นาฬิกาบันทึกเอง), `legacy` (แปลงจากไฟล์เก่า) |
| `subject`, `operator` | ผู้ตอบ / ผู้ถาม |
| `question_no`, `watch_qid` | ข้อที่เท่าไรในรอบ / qid ที่ส่งให้นาฬิกา (ดูข้อ 1) |
| `mode` | fix / manual / live / watch / legacy (ดูข้อ 1) |
| `question_text` | ข้อความคำถาม (ถ้าพิมพ์ไว้ — หน้าใช้งานจริง) |
| `label` | เฉลย: truth / lie / unknown / aborted |
| `feedback` | เฉพาะ mode = live: นาฬิกาตอบ `correct` ถูก / `wrong` ผิด / `unknown` ไม่ทราบ / `inconclusive` นาฬิกาตอบไม่แน่ชัดแต่ผู้ใช้บอกคำตอบจริง |
| `verdict` | คำตัดสินของนาฬิกา: truth / lie / inconclusive / invalid |
| `p_lie` | โอกาสโกหก 0–1 ที่นาฬิกาคำนวณ (≥ 0.65 = โกหก, ≤ 0.35 = จริง ตามค่าตั้งเริ่มต้น) |
| `decided_by` | ตัดสินด้วยอะไร: `rules` สูตรมาตรฐาน, `rules_calibrated` สูตรที่ปรับจากข้อควบคุม, `ai_model` โมเดล AI |
| `quality` | คุณภาพสัญญาณ 0–100 |
| `reasons` | bit เหตุผลที่ผลเชื่อถือได้น้อย (ดูข้อ 7) |
| `ok_mask` | bit สัญญาณที่ใช้ได้ในข้อนี้ (ดูข้อ 7 — ว่างในแถวที่แปลงจากไฟล์เก่า) |
| `gsr_ok`, `ppg_ok` | 1 = ข้อนี้มีสัญญาณ GSR / ชีพจร (เป็น feature ของ AI ด้วย) |
| `used_for_training` | 1 = ใช้เทรนได้ (รู้เฉลย + สัญญาณใช้ได้) — **แก้เป็น 0 เองได้** ถ้าไม่อยากให้ข้อนี้ถูกใช้ |
| `d_gsr` | GSR ที่พุ่งขึ้นสูงสุดหลังถาม เทียบ 3 วินาทีก่อนถาม (µS) |
| `d_hr` | ชีพจรที่เร่งขึ้นสูงสุด (bpm) |
| `d_amp` | แรงชีพจรปลายนิ้วที่ลดลง เป็นสัดส่วน (0.2 = ลด 20% = หลอดเลือดหดตัว) |
| `d_trm` | การสั่นของมือที่เพิ่มขึ้นเฉลี่ย (m/s²) |
| `d_tmp` | อุณหภูมิผิวที่เย็นลง (°C) |
| `z_gsr` … `z_tmp` | ค่า d_* แปลงเป็น z-score: (ค่า − ค่าเฉลี่ยตอนพัก) ÷ ความแกว่งตอนพัก ซึ่งคำนวณจากการเลื่อนหน้าต่าง 12 วินาทีไปตลอดช่วง baseline — z = 3 แปลว่าเปลี่ยนมากกว่าตอนนั่งเฉย ๆ 3 เท่า |
| `note` | หมายเหตุ เช่น เหตุผลที่ไม่ใช้เทรน, ไฟล์ที่นำเข้ามา |

**feature 12 ตัวที่ AI ใช้** = `z_gsr z_hr z_amp z_trm z_tmp d_gsr d_hr d_amp d_trm d_tmp gsr_ok ppg_ok`
ค่า d_/z_ ในไฟล์นี้คือ "ค่าที่ AI เห็นจริง": สัญญาณที่ใช้ไม่ได้ในข้อนั้นถูกตั้งเป็น 0 เหมือน `ml::extract()` ในนาฬิกา

**note ที่ขึ้นต้นด้วย `stale:`** — ผลค้างจากรอบก่อน (บั๊กของ Studio 2.2: qid 600, 601 ... ถูกใช้ซ้ำทุกรอบ และผลเก่าในประวัติของนาฬิกา
ถูกจับคู่กับข้อใหม่) แถวเหล่านี้ถูกตั้ง `used_for_training = 0` ไว้แล้ว — ผลจริงของข้อนั้นอยู่ในไฟล์ที่ดึงจากนาฬิกา (note บอกว่าเป็นข้อไหนของรอบไหน)
Studio 2.3 แก้แล้ว: จำเลข `seq` ของผลล่าสุดก่อนกดถาม แล้วรับเฉพาะผลที่ใหม่กว่า

**ไฟล์รวม** (ปุ่ม "รวมทุกไฟล์เป็นไฟล์เดียว") ชื่อ `result_all_<เวลา>.csv` คอลัมน์เหมือนข้างบนทุกอย่าง สร้างตอนกดดาวน์โหลดเท่านั้น
ไม่เก็บไว้ใน `data/` (ไม่งั้นข้อเดิมจะถูกนับซ้ำ) — ถ้าส่งไฟล์รวมกับไฟล์ต้นฉบับให้ train.py พร้อมกัน ข้อซ้ำจะถูกตัดด้วย `run_id + question_no`

## 4. `/train.csv` ในนาฬิกา (ข้อมูลที่นาฬิกาบันทึกเอง)

นาฬิกาบันทึกเองเมื่ออยู่ **โหมด train** และข้อนั้นเป็นข้อควบคุมที่รู้เฉลย (ถามจากหน้าเว็บนาฬิกา, ปุ่ม, Serial หรือ Studio โหมด fix)
ดาวน์โหลดได้ 3 ทาง แล้วจะถูกแปลงเป็น `result_*.csv` เสมอ (เฉพาะข้อที่ยังไม่มี):
ปุ่ม "ดึงข้อมูลที่นาฬิกาบันทึกเอง" ในหน้า "ข้อมูล & เทรน AI" · ปุ่ม `d` ใน collect_data.bat · `train_ai.bat --download`
(ปุ่ม "ดาวน์โหลด CSV" บนหน้าเว็บนาฬิกาได้ไฟล์ `polygraph_train.csv` → ใช้ปุ่ม "นำเข้าไฟล์ CSV" ใน Studio)

| คอลัมน์ | ความหมาย |
|---|---|
| `time` | เวลา (epoch วินาที, 0 = นาฬิกายังไม่รู้เวลา) |
| `subject` | ผู้ถูกทดสอบ (ตั้งที่หน้าเว็บนาฬิกา) |
| `qid` | qid ของข้อ |
| `label` / `label_name` | 0 = truth, 1 = lie |
| `quality`, `gsr_ok`, `ppg_ok`, `z_*`, `d_*` | เหมือนข้อ 3 |
| `p_model` | โอกาสโกหกที่นาฬิกาคำนวณตอนเก็บ → กลายเป็น `p_lie` |
| `source` | 0 สูตรมาตรฐาน, 1 สูตรปรับจากข้อควบคุม, 2 โมเดล AI → กลายเป็น `decided_by` |

## 6. ฐานข้อมูล `data/studio.db` (SQLite — เปิดด้วย DBeaver ได้)

แนะนำให้เปิด **VIEW** ก่อน เพราะแปลงเวลาเป็นวันที่และรวมตารางให้แล้ว

| VIEW | ใช้ดูอะไร |
|---|---|
| `v_sessions_overview` | ทุกเซสชัน: เวลาเริ่ม/จบ ผู้ถูกทดสอบ จำนวนข้อ จำนวนที่ตัดสินว่าโกหก/จริง |
| `v_question_results` | ทุกคำถาม + คำตอบ + คำตัดสิน + p_lie เรียงตามข้อ |
| `v_training_questions` | ทุกข้อจากหน้าเก็บข้อมูลเทรน AI / ใช้งานจริง + เฉลย + คำตัดสินของนาฬิกา |

| ตาราง | 1 แถว = | คอลัมน์สำคัญ |
|---|---|---|
| `sessions` | 1 การทดสอบ | `created/ended` (epoch), `subject`, `operator`, `template` (ชุดคำถาม), `device`, `fw` |
| `questions` | 1 คำถาม | `session_id`, `ord` (ลำดับข้อ), `qid`, `kind`, `text`, `asked_at`, `answer` (yes/no) |
| `results` | 1 ผลจากนาฬิกา | `question_id`, `verdict`, `p` (โอกาสโกหก), `quality`, `reasons`, `ok`, `data` (JSON เต็ม) |
| `samples` | ค่าสัญญาณ 1 ครั้ง (5/วินาที) | `t`, `question_id`, `phase`, `heart_rate_bpm`, `hrv_ms`, `gsr_us`, `gsr_phasic_us`, `skin_temp_c`, `tremor_ms2`, `motion_ms2`, `stress_index`, `engine_state`, `ppg_contact`, `gsr_contact`, `battery_mv` |
| `events` | 1 เหตุการณ์ | `type` (เช่น ask, cmd_baseline, device_reboot, low_batt), `data` (JSON) |
| `training_runs` | 1 รอบเก็บข้อมูล/ใช้งานจริง | `run_id` (ตรงกับชื่อไฟล์ result_<run_id>.csv), `subject`, `operator`, `mode` (fix/manual/live), `signals_file`, `results_file` |
| `training_questions` | 1 ข้อในรอบ | `question_no`, `watch_qid`, `mode`, `label`, `verdict`, `p_lie`, `decided_by`, `used_for_training`, `data` (JSON ผลเต็ม + feedback + question_text) |

ไฟล์ CSV คือ "ต้นฉบับ" ที่ใช้เทรน — ตาราง training_* เป็นสำเนาไว้ query ใน DBeaver (ข้อที่นำเข้า/ดึงจากนาฬิกาไม่ได้อยู่ในตาราง)

ฐานข้อมูลจาก Studio รุ่นก่อน (คอลัมน์ `hr, gsr, tmp ...`) ถูกเปลี่ยนชื่อเป็นแบบเต็มให้อัตโนมัติตอนเปิด Studio รุ่นนี้ครั้งแรก ข้อมูลเดิมอยู่ครบ

## 7. ค่าแบบ bit (ตัวเลขที่รวมหลายสถานะ)

**`reasons`** — เหตุผลที่ผลเชื่อถือได้น้อย (บวกกันได้ เช่น 5 = 1 + 4)

| bit | ค่า | ความหมาย |
|---|---|---|
| 0 | 1 | ไม่มีสัญญาณ GSR (ระบบใช้สัญญาณอื่นแทน — ยังตัดสินได้) |
| 1 | 2 | เซนเซอร์ชีพจรไม่แตะผิว |
| 2 | 4 | ขยับตัวมากเกินไป → ข้อนี้ใช้ไม่ได้ |
| 3 | 8 | ข้อมูลก่อนถามไม่พอ (ถามติดกันเร็วเกินไป) → ใช้ไม่ได้ |

**`ok`** — สัญญาณที่ใช้ได้ในข้อนั้น: bit 0 GSR, 1 ชีพจร, 2 แรงชีพจร, 3 การสั่น, 4 อุณหภูมิ (31 = ใช้ได้ครบ 5 ตัว)

## 8. ข้อมูลสดจากนาฬิกา (JSON ทาง UDP / `/api/live`) — ชื่อย่อเพื่อประหยัดขนาดแพ็กเก็ต

| คีย์ | ความหมาย | คีย์ | ความหมาย |
|---|---|---|---|
| `hr` | ชีพจร bpm | `es` | สถานะ engine 0–3 |
| `hrv` | HRV ms | `ep` | ความคืบหน้าของ baseline/คำถาม 0–1 |
| `con` | เซนเซอร์ชีพจรแตะผิว | `eq` | qid ที่กำลังถาม |
| `gsr` `gt` `gp` | GSR รวม / tonic / phasic µS | `rs` | ลำดับผลล่าสุด (เปลี่ยน = มีผลใหม่) |
| `gc` | แผ่น GSR แตะผิว | `set` | ร่างกายกลับสู่ปกติแล้ว พร้อมถามข้อถัดไป |
| `tmp` | อุณหภูมิผิว °C | `md` | โหมดนาฬิกา 0 ใช้งานจริง / 1 เก็บข้อมูล |
| `trm` | มือสั่น m/s² | `ml` | 1 = ติดตั้งโมเดล AI แล้ว |
| `mot` | การขยับตัว m/s² | `sby` `wp` `eco` | ตั้งค่าการหลับ (นาที) / กำลังส่ง WiFi / ECO |
| `si` | ดัชนีความตื่นตัว 0–100 | `vb` `bp` `bat` | แบต mV / % / มีแบต |
